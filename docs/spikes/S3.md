# S3 — Edalize + cocotb + Verilator (and Icarus) on macOS and Linux

**Question (IMPLEMENTATION_PLAN.md):** does Edalize 0.6 + cocotb 2.1 + Verilator 5.052 run
a testbench on macOS and Linux? It decides how M2-05 (`adapters/tool/edalize.py`: Edalize
sim for Verilator and Icarus, a cocotb runner, a cocotb results parser) is built.

**Status:** done on macOS (arm64) and Linux arm64 (the `chipgraph-base` stage of
`docker/Dockerfile` in a local container), 2026-10-09. CI Linux (ubuntu-latest, amd64)
is wired in `.github/workflows/spike-s3.yml` and left for the reviewer (last section).

**Answer:** yes, with two conditions. Edalize 0.6.8's own cocotb run does not work with
cocotb 2.1, so chipgraph uses Edalize only to *configure*, then runs `make` and the
simulator through its `Runner` with an environment it computes itself. And a failing
test never changes an exit code: `results.xml` is the only signal.

## Pitfalls, with the fix

1. **Edalize 0.6.8's cocotb run is broken with cocotb 2.1.** `Sim.run()` sets
   `COCOTB_TEST_MODULES`, `LIBPYTHON_LOC` and `PYGPI_PYTHON_BIN`, but cocotb 2.x's GPI
   reads only `GPI_USERS` (`LIBPYTHON_LOC` is read by cocotb's Makefiles, not the GPI). The
   model prints `ERROR gpi ... No GPI_USERS specified, exiting...`, writes no
   `results.xml` and **exits 0**: `make`/Edalize report success. Edalize `main`
   (unreleased) adds a missing-`results.xml` check but still no `GPI_USERS`. Fix: do not
   call `Sim.run()`; set the run environment yourself (as `cocotb_tools.runner` does):

   ```text
   GPI_USERS=<find_libpython.find_libpython()>;<cocotb_tools.config.pygpi_entry_point()>
   PYGPI_PYTHON_BIN=<sys.executable>   COCOTB_TEST_MODULES=<module>   COCOTB_TOPLEVEL=<top>
   TOPLEVEL_LANG=verilog   PYTHONPATH=<test dir>:<sys.path>   COCOTB_RESULTS_FILE=<work>/results.xml
   COCOTB_TRUST_INERTIAL_WRITES=1   (Verilator only; what cocotb's runner sets)
   ```

2. **A green exit code means nothing.** Failing tests, import errors and a GPI that never
   loaded all exit 0 (Verilator and Icarus). The parser must read `results.xml`, and a
   missing or empty one is `error`, never `pass`.
3. **`cocotb-config` in backticks.** Edalize writes `` `cocotb-config --lib-dir` `` etc. into
   the Makefile and `.vc`, so `make` resolves it from `PATH`. OSS CAD Suite's `bin/` has its
   own `cocotb-config` (its bundled cocotb 2.1.0.dev0 on Python 3.11). Fix: put the venv's
   `bin` (`Path(sys.executable).parent`) first on the `PATH` passed to the Runner.
4. **OSS CAD Suite's Icarus cannot load a pip-installed cocotb.** Its `bin/vvp` is a
   wrapper: `PYTHONHOME=<suite>` and `exec <suite>/lib/ld-linux-*.so.1 --inhibit-rpath ""
   --library-path <suite>/lib <suite>/libexec/vvp`, so cocotb's VPI module links the
   suite's `libgpi.so` and fails: `libcocotbvpi_icarus.so: undefined symbol:
   gpi_debug_enabled`; no test runs, exit 0. Fix: use the distribution's Icarus
   (`apt-get install iverilog`, 11.0 on bookworm, passes everything) ahead of the suite on
   `PATH`. Verilator from the suite is fine (the model is a plain executable).
5. **The chipgraph-eda image cannot build a Verilator model.** `bookworm-slim` has no C++
   compiler (`g++: missing`); on arm64 even `pip install cocotb` fails (no wheel, sdist
   needs `c++`). Fix for M2-05/the image: `apt-get install g++ liblz4-dev zlib1g-dev
   iverilog` (lz4/zlib only for FST).
6. **macOS: old Command Line Tools default to C++98.** The Homebrew Verilator 5.052 bottle
   was built with Apple clang 21 and its `verilated.mk` has an empty `CFG_CXXFLAGS_STD`
   (no `-std=` flag); with CLT 16.2 (`__cplusplus 199711L`) the model fails with
   `"Verilator requires a C++14 or newer compiler"`. Fix: `verilator -CFLAGS -std=gnu++17`
   (Edalize: `verilator_options`; cocotb runner: `build_args`), or update the Command Line
   Tools. `s3_common.verilator_cxx_std_args()` adds the flag only when
   `c++ -dM -E -x c++ /dev/null` reports < C++14; a `chipgraph doctor` check fits.
7. **macOS: FST needs Homebrew's lz4 on the compile line.** Verilator 5.052's FST writer
   includes `<lz4.h>` and links `-llz4 -lz`; Apple clang does not search `/opt/homebrew`:
   `fatal error: 'lz4.h' file not found`. Fix: `-CFLAGS -I/opt/homebrew/include -LDFLAGS
   -L/opt/homebrew/lib` (or VCD, which needs nothing). Linux: `liblz4-dev zlib1g-dev`.
8. **Icarus needs SystemVerilog and a timescale.** tinysoc uses `logic`/`always_ff`/
   `unique case`: `iverilog_options: [-g2012]` (Edalize does not add it for
   `systemVerilogSource`), and `timescale: 1ns/1ps`, since Icarus defaults to 1 s and a
   10 ns cocotb clock is not representable. Icarus warns `Case unique/unique0 qualities
   are ignored` (harmless).
9. **Edalize in cocotb mode renames the Verilator top** to `Vtop` (`--prefix Vtop`, as
   cocotb's `verilator.cpp` needs), so the executable is `./Vtop`, not `./V<toplevel>`.
10. **libpython on macOS** (the classic failure) did not occur: `find_libpython` found the
    right library for uv-managed (`.../lib/libpython3.1x.dylib`) and Homebrew framework
    builds (`.../Python.framework/Versions/3.1x/Python`). A libpython that is missing or
    of another version than `PYGPI_PYTHON_BIN` gives no `results.xml` and exit 0 (checked
    by hand), which pitfall 2 already catches. Cosmetic: cocotb's
    `Using Python 3.14.6 interpreter` log line shows the same version for 3.14.0 and 3.14.3
    (3.13.14 for both 3.13s), so it is not the running interpreter's version.

## How chipgraph would call it (M2-05)

**(i) In-process or `make`?** Both, split. `Sim(edam, work_root).configure()` is pure
Python and starts **no subprocess** for `verilator` and `icarus` (`probe_configure.py`:
`subprocess.Popen` spied, zero calls); it writes the Makefile and tool files. Everything
that runs a program then goes through the `Runner`:

```python
flow = Sim(edam, work_root)  # in-process, no subprocess
flow.configure()
# ("make", flow_make_options)
make, make_args = flow.build_runner.get_build_command()
# Verilator: ("./Vtop", run_options, work_root); Icarus: ("make", ["run"], work_root)
cmd, args, cwd = flow.flow.get_node(tool).inst.run()
await ctx.runner.run([make, *make_args], cwd=work_root, env=env)
await ctx.runner.run([cmd, *args], cwd=Path(cwd), env=env)
```

Never call `flow.build()`/`flow.run()`: they call `subprocess.run` directly (bypassing the
`Runner`, its timeout and log capture) and `run()` is broken with cocotb 2.1 (pitfall 1).
The work root belongs to the run state, outside the project's tracked files.

**(ii) Files written.** By `configure()`: `Makefile`; Verilator `<name>.vc`; Icarus
`<name>.scr` and `timescale.v` (only with the `timescale` option). They are identical
across two work roots for the same EDAM (`probe_configure.py`), but they embed absolute
source paths and backticked `cocotb-config` calls, so they are not a portable key. By the
build: Verilator `Vtop*.{cpp,h,mk}`, objects and `./Vtop`; Icarus the `vvp` image
`<name>`. By the run: `results.xml` (at `COCOTB_RESULTS_FILE`) and `dump.fst` with waves.
Idempotency key inputs: the normalised EDAM (paths relative to `repo_root` plus the
sha256 of every source and of the test module(s)), `toplevel`, parameters/defines/
plusargs, the tool options, `COCOTB_TEST_MODULES`/`COCOTB_TEST_FILTER`, a fixed
`COCOTB_RANDOM_SEED` (cocotb seeds randomly otherwise), and the versions of edalize,
cocotb and the simulator. Not inputs: `results.xml` (timestamp, hostname, seed,
`sim_time_ratio`) and build products.

**(iii) Environment.** The block in pitfall 1, computed in-process from
`cocotb_tools.config` and `find_libpython` (no `cocotb-config` subprocess), plus `PATH`
with the venv's `bin` first (pitfall 3). On macOS nothing else (no `DYLD_*`): the
Verilator model gets cocotb's lib dir as `-rpath` from Edalize's `-LDFLAGS`. Icarus loads
the VPI module by path (`-M <lib dir> -m cocotbvpi_icarus`). If `find_libpython` returns
`None`, return `error` before building ("Python built without a shared libpython").

**(iv) Parser.** `parse_results.py`, drafted against the real failing runs above:

- build exit ≠ 0 → `error`; issues from the build log (chipgraph's `VerilatorParser` for
  `%Error: f:l:c: msg`, a small one for Icarus `f:l: syntax error`/`f:l: error: msg`);
- no `results.xml`, invalid XML or zero `testcase` → `error`, with the last Python
  exception or `ERROR gpi` line of the run log as the message;
- each `testcase` with `<failure>` (or `<error>`) → one `Issue`: `file`/`line` = the
  last traceback frame in the test's own file (the `file` property; the `line` property
  is the `def` line, used only as a fallback), `rule = cocotb/<type>` (`AssertionError`
  = the DUT is wrong; other types usually mean the testbench is), `msg = <classname>.<name>:
  <message>`; `<skipped>` → `info`; any failure → `fail`;
- all pass but run exit ≠ 0 → `error`; else `pass`.

`CheckResult` (frozen) has no `tests[]`, while DESIGN.md 7.1 lists `sim` → `{status,
tests[{name,pass,log_tail}]}`. Per-test pass/fail fits `issues` (failures) and
`log_tail`; a real `tests[]` needs a contract change (an ADR), not M2-05.

## Recommendation for M2-05

- **Shape:** Edalize in-process for `configure()` only; `make` and the simulator through
  `ctx.runner`; the cocotb env computed by chipgraph (pitfall 1); `results.xml` parsed
  into `CheckResult`. Not cocotb's runner: it calls `subprocess` itself and duplicates
  what Edalize already knows (filelists, tool options, more simulators). The env it sets
  (`Runner._set_env_common`/`_set_env_test`) is the reference for chipgraph's.
- **`adapters/tool/edalize.py`:** EDAM from the block's filelist (`files`, `toplevel`,
  `parameters`), `flow_options = {tool, cocotb_module, ...}` with per-tool defaults
  (Verilator: the C++ std fix when needed; Icarus: `-g2012`, `timescale`), the work
  root under the run state, the two Runner calls, the parser, timeout from `spec.args`.
  Waves opt-in (`--trace-fst` + `--trace` / the dump top for Icarus).
- **Parser:** a separate `cocotb` parser module (it reads XML, not a log, so not the
  `LogParser` protocol). That is outside M2-05's `writes` (`adapters/tool/edalize.py`):
  either keep it private in `edalize.py` or add `adapters/parser/cocotb.py` to the task.
- **Pins in `pyproject.toml`:** a new extra, `sim = ["edalize==0.6.8", "cocotb==2.1.0"]`
  (exact: cocotb's GPI env contract changed between 1.x and 2.x and Edalize's cocotb glue
  lags it), and the `edalize` entry point under `chipgraph.adapters.tool`. Both are
  outside `writes` too.
- **Icarus in v1:** yes, cheap: builds in < 0.1 s, needs no C++ compiler, same parser. But
  from the distribution (apt/Homebrew), not OSS CAD Suite (pitfall 4).
- **CI/image:** the accept ("runs on CI Linux") needs `g++`, `liblz4-dev`, `zlib1g-dev`
  and apt `iverilog` either in the `ci.yml` job or in `docker/Dockerfile`, both outside
  `writes`. The plan's S3 row now lists these extra files for M2-05.
